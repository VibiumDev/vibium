# Client Conformance Suite

**Goal:** Make the client contract executable, so a client that drifts from the protocol fails a test instead of a user's script. Adding Ruby (#68), C# (#90), Nim, or Rust should then be a weekend rather than a liability.

**Status:** Not started. Written 2026-08-05.

---

## Why

The contract exists only as prose, and the clients have already diverged from it.

**A shipped method that cannot work.** Java's `expose(String name, Function<Object[], Object>)` sends only `name` — no `fn` — so the server answers `fn is required`. It also subscribes to a `vibium:page.exposedFunction` event the server has never emitted, and carries `// TODO: send result back if bidirectional exposed functions are supported`. It has never worked in any release. Found in #135, only because a user reported it.

**Coverage is lopsided.** 35 test files for JS, 33 for Python, 15 for Java. The thinnest-tested client is the one that shipped the broken method. Nobody could see that, because "test files" is not a measure of contract coverage.

**Drift has recurred.** #167 already fixed "Java client command/param mismatches" once.

**The contract is ambiguous about its own wire format.** `api.md` lists 114 implemented `vibium:` methods, but its Protocol column mixes granularity: dialog accept appears as `browsingContext.handleUserPrompt` (row 137) while the router also accepts `vibium:dialog.accept`. A client author cannot tell which is canonical, and nothing checks either way.

None of this is a Java problem. It is what happens when three implementations of a 114-method protocol are verified only by hand-written tests that each author chose independently.

---

## Design

Three layers, each independently useful. Ship them in order; stop whenever the value runs out.

### Layer 1 — Manifest

A machine-readable description of the protocol, generated from Go so it cannot drift from the implementation.

```
docs/reference/protocol.json      generated, checked in
```

For every method: name, aliases, required and optional params with types, response shape, and whether it needs a context. Generated by walking the `case "vibium:..."` arms in `api/router.go` and the handler signatures they dispatch to.

Checked in so clients in other repos can consume it, and so a diff shows up in review when the protocol changes.

- [ ] `make protocol-manifest` target that regenerates it
- [ ] CI fails if the checked-in manifest is stale, the same way a `go.sum` drift would

### Layer 2 — Wire recorder and coverage report

The cheapest way to measure drift: watch what each client actually sends while running *its own existing tests*, then compare against the manifest.

```
tests/conformance/record.js        wraps a client run, captures ndjson both ways
tests/conformance/report.js        manifest coverage + param validation
```

No client changes. Point it at `make test-js`, `make test-python`, `make test-java` and it answers:

- which manifest methods the client never exercises
- which methods it sends with params that do not match the manifest
- which methods it sends that the manifest does not contain

Java's `expose` fails the second check immediately: it sends `{name}` where the manifest requires `{name, fn}`. So does any future method that silently loses a parameter.

Output a per-client coverage number in contract terms, replacing "35 vs 15 test files" with something comparable.

- [ ] recorder that proxies stdio between client and binary, teeing both directions
- [ ] report that diffs observed traffic against the manifest
- [ ] `make conformance` runs all three clients and prints the table
- [ ] CI publishes the numbers; failing on regression comes later, once a baseline exists

### Layer 3 — Shared battery for new clients

Layer 2 measures existing clients. Layer 3 is what a *new* client implements to prove itself.

```
tests/conformance/cases/*.json     language-agnostic scenarios
```

Each case is a sequence of operations and expected wire messages, written against the manifest rather than any language:

```json
{
  "name": "page.expose sends name and fn",
  "steps": [
    { "call": "page.expose", "args": { "name": "add", "fn": "(a,b) => a+b" },
      "expect_wire": { "method": "vibium:page.expose",
                       "params": { "name": "add", "fn": "(a,b) => a+b" } } }
  ]
}
```

A new client implements one small driver that maps `"page.expose"` to its own binding and runs the cases. That driver is the only per-language work, and it is the thing that would have caught Java's `expose` before release.

Naming is checked against the convention table already in the client implementation guide (line 222), so `page.setViewport` must surface as `setViewport()` in JS and Nim, `set_viewport()` in Python and Ruby, `isVisible()` in Nim but `visible?` in Ruby.

- [ ] case format and a driver contract documented in the client implementation guide
- [ ] cases covering every manifest method
- [ ] JS driver as the reference implementation
- [ ] Python and Java drivers, which will surface the existing gaps

---

## Constraints

- Go stdlib only for the generator; no new dependencies.
- The recorder must not require client changes. If it does, it is the wrong design — the point is to measure what clients already do.
- Cases are data, not code. A case that needs a language-specific escape hatch belongs in that client's own suite.
- Do not fail CI on Layer 2 until a baseline is recorded. The first run will be red for Java, and that is information, not a build break.
- No external sites. Use `tests/helpers/test-server.js`, per the existing rule.

---

## Expected findings on first run

Worth writing down now so they are predictions rather than hindsight:

1. Java's `expose` sends `{name}` against a manifest requiring `{name, fn}`.
2. Java's method coverage is well below JS and Python — 15 test files against 35 suggests large unexercised areas, not merely denser tests.
3. Some `vibium:` methods are exercised by no client at all, only by the CLI or MCP.
4. The `api.md` Protocol column disagrees with the manifest wherever it names a BiDi command instead of the `vibium:` extension.

If (1) and (2) do not appear, the recorder is not seeing everything and should be fixed before the numbers are trusted.
